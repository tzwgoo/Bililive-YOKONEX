# Bilibili 直播礼物互动程序设计文档

## 1. 背景

本项目需要基于哔哩哔哩直播开放平台官方文档，开发一个 Python 程序，用于接入单直播间的互动消息，并通过本地 Web 面板实时展示互动数据。

本次设计只以官方开放平台文档为准，不复用仓库中现有的 `docs/WEBSOCKET_API.md`。

涉及的官方能力包括：

- HTTP 鉴权与接口调用
- 项目开启 `POST /v2/app/start`
- 项目心跳 `POST /v2/app/heartbeat`
- 项目关闭 `POST /v2/app/end`
- 官方 WebSocket 长连
- 直播间事件监听

## 2. 目标

首版需要交付一个“可演示、可长期运行”的最小可用版本，满足以下目标：

- 使用 Python 实现
- 提供本地 Web 面板
- 从 `.env` 读取 `app_id`、`access_key_id`、`access_key_secret`
- 在面板中输入主播身份码 `code`
- 成功连接官方开放平台并建立互动场次
- 实时监听并展示以下事件：
  - 礼物 `LIVE_OPEN_PLATFORM_SEND_GIFT`
  - 弹幕 `LIVE_OPEN_PLATFORM_DM`
  - 点赞 `LIVE_OPEN_PLATFORM_LIKE`
- 同时维护项目心跳和长连心跳
- 支持断线自动重连
- 支持优雅停止，并主动调用 `end`
- 记录基础运行日志

## 3. 已确认范围

### 3.1 首版范围

- 单直播间
- 单会话
- 单服务实例
- 本地运行
- 本地浏览器访问面板
- 单次仅监听一个主播身份码对应的直播间

### 3.2 首版不做

- 多直播间并发管理
- 多主播快速切换历史管理
- 数据库存储
- 登录鉴权系统
- 告警通知
- 报表统计
- 权限管理
- 审计后台

## 4. 技术选型

推荐技术栈如下：

- Python 3.11+
- FastAPI：提供本地 HTTP 服务与页面接口
- Uvicorn：运行服务
- Jinja2：渲染本地 HTML 页面
- 原生 JavaScript：实现页面交互与实时刷新
- `httpx`：调用官方 HTTP API
- `websockets`：连接官方 WebSocket
- `asyncio`：统一管理后台任务、心跳、重连
- `python-dotenv`：读取 `.env`
- `pydantic`：配置与数据模型校验
- `pytest`：测试

选择该方案的原因：

- FastAPI 与 `asyncio` 对“HTTP 请求 + 长连 + 定时任务 + 本地面板”组合最自然
- 后续扩展日志、健康检查、事件广播、接口开放都较顺手
- 比 Flask/线程模型更适合需要稳定维护 WebSocket 会话的场景

## 5. 总体架构

系统拆分为四层：

### 5.1 配置层

负责读取和校验运行配置。

核心职责：

- 读取 `.env`
- 校验必填项是否存在
- 统一向上提供配置对象

### 5.2 B 站接入层

负责所有与官方开放平台协议直接相关的内容。

核心职责：

- 生成签名
- 调用 `start / heartbeat / end`
- 处理官方 WebSocket 协议头
- 发送 `OP_AUTH`
- 发送长连心跳
- 解析普通包与压缩包
- 解析礼物、弹幕、点赞事件

### 5.3 会话服务层

负责单直播间生命周期管理。

核心职责：

- 创建并维护当前会话
- 保存 `game_id`、房间号、主播信息、最近心跳时间
- 启动项目心跳任务
- 启动长连监听任务
- 处理断线重连
- 处理停止逻辑
- 将原始事件转换为前端友好的结构

### 5.4 Web 面板层

负责本地可视化与操作入口。

核心职责：

- 展示配置状态
- 输入主播身份码
- 启动和停止监听
- 展示服务状态
- 展示主播和房间信息
- 实时展示礼物、弹幕、点赞事件

## 6. 模块划分

建议文件结构如下：

```text
app/
  main.py
  config.py
  models.py
  api/
    routes.py
  bilibili/
    signature.py
    http_client.py
    ws_protocol.py
    ws_client.py
  services/
    event_hub.py
    live_session.py
  templates/
    index.html
  static/
    app.js
    style.css
logs/
tests/
.env.example
```

各文件职责如下：

### 6.1 `app/main.py`

- FastAPI 应用入口
- 注册路由、静态文件、模板
- 注册启动与关闭钩子

### 6.2 `app/config.py`

- 定义配置模型
- 加载 `.env`
- 检查必填配置项

### 6.3 `app/models.py`

- 定义会话状态枚举
- 定义礼物、弹幕、点赞事件模型
- 定义前端响应模型

### 6.4 `app/bilibili/signature.py`

- 计算请求体 MD5
- 组装 `x-bili-*` 请求头
- 生成 HMAC-SHA256 签名

### 6.5 `app/bilibili/http_client.py`

- 封装官方 HTTP 接口调用
- 对错误码和错误信息做统一返回

### 6.6 `app/bilibili/ws_protocol.py`

- 构造协议头
- 解析协议头
- 处理大端字节序
- 处理 `version=0` 和 `version=2`
- 解压 zlib 数据
- 支持多 proto 包递归拆分

### 6.7 `app/bilibili/ws_client.py`

- 连接 `wss_link`
- 发送鉴权包
- 发送长连心跳
- 读取消息并交给协议解析器
- 将 `cmd` 事件吐给会话服务层

### 6.8 `app/services/live_session.py`

- 单直播间会话管理器
- 维护状态机
- 控制启动、运行、重连、停止
- 维护项目心跳任务
- 接收并分发事件

### 6.9 `app/services/event_hub.py`

- 缓存最近事件
- 将新事件广播给前端
- 为前端提供事件流订阅

### 6.10 `app/api/routes.py`

- 首页
- 启动监听接口
- 停止监听接口
- 会话状态接口
- 实时事件接口

## 7. 运行流程

### 7.1 服务启动阶段

1. 启动 FastAPI 服务
2. 读取 `.env`
3. 校验 `APP_ID`、`BILI_ACCESS_KEY_ID`、`BILI_ACCESS_KEY_SECRET`
4. 初始化会话服务
5. 打开本地面板

### 7.2 用户启动监听阶段

1. 用户打开本地面板
2. 用户输入主播身份码 `code`
3. 前端调用本地启动接口
4. 后端使用 `app_id + code` 调用官方 `start`
5. 官方返回：
   - `game_id`
   - `websocket_info.auth_body`
   - `websocket_info.wss_link`
   - 主播信息
6. 会话服务保存当前场次信息
7. 建立官方 WebSocket 长连
8. 发送 `OP_AUTH`
9. 开始长连心跳
10. 开始项目心跳
11. 前端看到状态切换为“运行中”

### 7.3 实时事件阶段

长连收到消息后：

1. 解析协议包头
2. 如为压缩包则解压
3. 递归拆出实际消息体
4. 识别 `cmd`
5. 只处理礼物、弹幕、点赞三类事件
6. 标准化成统一事件对象
7. 推送给面板
8. 面板实时刷新

### 7.4 停止阶段

1. 用户点击“停止监听”
2. 停止长连心跳任务
3. 停止项目心跳任务
4. 调用官方 `end`
5. 关闭当前 WebSocket
6. 清理当前会话状态
7. 前端状态切换为“已停止”

## 8. 状态机设计

会话状态建议定义为：

- `idle`：未启动
- `starting`：启动中
- `running`：运行中
- `reconnecting`：重连中
- `stopping`：停止中
- `error`：异常

状态切换规则：

- `idle -> starting`
- `starting -> running`
- `running -> reconnecting`
- `reconnecting -> running`
- `running -> stopping`
- `stopping -> idle`
- 任意状态在不可恢复错误下可进入 `error`

## 9. 前端面板设计

页面采用单页结构，分为三块：

### 9.1 配置与控制区

展示：

- `.env` 配置是否完整
- 主播身份码输入框
- 启动监听按钮
- 停止监听按钮

行为规则：

- 如果 `.env` 配置缺失，禁止启动
- 如果当前已有会话在运行，禁止再次启动

### 9.2 状态区

展示：

- 当前状态
- 主播昵称
- 房间号
- `game_id`
- 最近项目心跳时间
- 最近长连消息时间
- 最近错误信息

### 9.3 实时事件区

拆为三个分页或三个卡片流：

- 礼物流
- 弹幕流
- 点赞流

展示策略：

- 时间倒序
- 只保留最近 N 条
- 礼物事件突出礼物名、数量、价值

## 10. 事件数据标准化

前端不直接消费 B 站原始结构，而是消费统一结构：

```json
{
  "event_type": "gift|danmaku|like",
  "cmd": "LIVE_OPEN_PLATFORM_SEND_GIFT",
  "room_id": 123,
  "open_id": "xxx",
  "uname": "用户昵称",
  "timestamp": 1714113037,
  "payload": {}
}
```

其中：

- `event_type` 用于前端分类渲染
- `payload` 存放各类事件特有字段

礼物事件 `payload` 至少包含：

- `gift_id`
- `gift_name`
- `gift_num`
- `price`
- `r_price`
- `paid`
- `gift_icon`
- `combo_gift`

弹幕事件 `payload` 至少包含：

- `msg`
- `msg_id`
- `fans_medal_level`
- `guard_level`

点赞事件 `payload` 至少包含：

- `like_text`
- `like_count`

## 11. 心跳与重连策略

### 11.1 项目心跳

- 周期：20 秒
- 调用接口：`POST /v2/app/heartbeat`
- 作用：维持 `game_id` 有效

### 11.2 长连心跳

- 周期：20 秒
- 包类型：`OP_HEARTBEAT`
- Body：空
- 作用：维持 WebSocket 连接有效

### 11.3 自动重连

当发生以下情况时进入重连：

- WebSocket 异常断开
- 长时间未收到消息且底层连接已断

重连策略：

1. 当前会话进入 `reconnecting`
2. 优先尝试当前地址
3. 若失败则尝试 `wss_link` 备用地址
4. 重连成功后恢复 `running`
5. 若项目心跳已失效，则结束当前会话并提示重新启动

说明：

- 如果收到 `LIVE_OPEN_PLATFORM_INTERACTION_END`，说明对应 `game_id` 已失效，不再尝试仅靠长连恢复，应终止当前会话

## 12. 错误处理

### 12.1 官方 HTTP 错误

需要显式处理并透出官方错误码，例如：

- `4002` 签名异常
- `4003` 请求过期
- `7003` 心跳过期
- `7007` 身份码错误
- `7010` 单直播间连接超过上限
- `8002` 项目无权限访问

策略：

- 后端保留原始错误码和消息
- 前端展示可读错误提示

### 12.2 WebSocket 事件级错误

需要处理：

- 鉴权失败
- 解压失败
- 包体解析失败
- 未识别 `cmd`

策略：

- 未识别 `cmd` 只记录日志，不中断服务
- 协议错误按严重程度决定是否断开重连

### 12.3 服务退出保护

服务关闭时尽量执行：

- 停止后台任务
- 调用 `end`
- 关闭 WebSocket

## 13. 日志设计

日志目录：

- `logs/`

建议输出内容：

- 服务启动日志
- 配置校验结果
- `start / heartbeat / end` 请求结果
- WebSocket 连接与重连日志
- 关键错误日志
- 收到的事件摘要日志

日志级别建议：

- `INFO`：启动、停止、重连、心跳成功
- `WARNING`：重试、短时异常、未知事件
- `ERROR`：签名失败、接口失败、协议解析失败

## 15. 风险与约束

### 15.1 平台限制

- 单直播间单应用连接数有限制
- 心跳失效会导致 `game_id` 失效
- 未正确调用 `end` 可能影响下一场互动

### 15.2 首版约束

- 单会话模型决定同一时间只能监听一个主播
- 不做持久化，刷新页面后仅保留当前后端缓存的最近事件

### 15.3 开发风险

- 官方长连协议包含压缩包和多消息嵌套，需要解析准确
- 自动重连不能误用已失效的 `game_id`

## 16. 实施建议

推荐按以下顺序实现：

1. 先完成配置加载和签名模块
2. 再完成 `start / heartbeat / end` HTTP 调用
3. 再完成 WebSocket 协议编解码
4. 再完成会话服务和双心跳
5. 最后接入本地 Web 面板

这样可以先把与官方平台的核心通信跑通，再接可视化层，降低联调复杂度。

## 17. 验收标准

满足以下条件即视为首版达标：

- `.env` 配置完整时服务能正常启动
- 页面能输入主播身份码并启动监听
- 能成功调用 `start`
- 能成功建立长连并完成鉴权
- 能持续发送双心跳
- 面板能实时展示礼物、弹幕、点赞
- 长连断开后能自动重连
- 点击停止后能调用 `end`
- 日志中能看到完整生命周期
